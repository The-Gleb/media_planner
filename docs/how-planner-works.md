# Как работает планнер: алгоритмы

Пять алгоритмов, в порядке использования. Обозначения в конце. Справочник с выводом формул и
привязкой к строкам кода — [`mathematical-model.md`](mathematical-model.md).

Границу знаний планнер не пересекает: на входе только каталог (публичные диапазоны), история
прошлых кампаний (то, что показывает рекламный кабинет) и факты текущей кампании. Скрытые параметры
симулятора планнер не видит.

---

## Алгоритм 1. Один час канала

Ядро всего: сколько канал даст за час при заданном бюджете. Используется и в планировании, и в
прогнозе, и в обучении на истории.

```text
Вход:  channel   — параметры канала (ctr, cr, cpm, daily_capacity, profile[24],
                   audience, threshold, price_growth, ctr_fatigue, freq_fatigue,
                   reach_decay, freq_reach_decay)
       state     — накопленный охват R и накопленные показы I канала
       budget    — деньги на этот час
       hour      — час суток
Выход: показы, новый охват, клики, конверсии, расход; state обновлён

1  depth      ← clamp((R / audience − threshold) / (1 − threshold), 0, 1)
2  excess     ← max(I / max(R, 1) − 1, 0)                 # частота сверх 1 показа на человека
3  cpm_hour   ← cpm · (1 + price_growth · depth²)          # цена растёт с глубиной выкупа
4  supply     ← daily_capacity · profile[hour]             # сколько запросов есть в этот час
5  imps       ← min(supply, budget · 1000 / cpm_hour)      # купить нельзя больше спроса
6  ctr_hour   ← ctr · exp(−ctr_fatigue · depth − freq_fatigue · excess)
7  p_new      ← (1 − depth)^reach_decay · exp(−freq_reach_decay · excess)
8  new_reach  ← min(imps · p_new, audience − R)
9  clicks     ← imps · ctr_hour
10 conv       ← clicks · cr
11 spend      ← imps · cpm_hour / 1000
12 R ← R + new_reach;  I ← I + imps
```

Интуиция: пока охват меньше порога, канал линейный. Дальше цена растёт, CTR устаёт, новых людей
меньше. Из-за этого нельзя «влить всё в лучший канал».

## Алгоритм 2. Задача A: бюджет → план

```text
Вход:  budget, horizon (часы), channels, metric ∈ {reach, clicks, conversions}
Выход: caps[channel][hour], expected[channel][hour], нераспределённый резерв

# 1. Кривая отклика каждого канала
1  for each channel c:
2      for each b in сетка бюджетов от 0 до ёмкости канала (128 точек, гуще у нуля):
3          kpi_c(b) ← сумма metric по часам horizon при прогоне Алгоритма 1
4                     с бюджетом b, разложенным по часам пропорционально profile
5      сделать kpi_c вогнутой (PAVA): предельный прирост не растёт с бюджетом

# 2. Жадное распределение по предельному приросту
6  alloc[c] ← 0 для всех c;  remaining ← budget
7  while remaining > 0:
8      c* ← канал с наибольшим (Δkpi / Δbudget) на следующем отрезке его кривой
9      if прирост c* ≤ 0: break                       # деньги остаются резервом
10     переложить отрезок кривой c* в alloc[c*], уменьшить remaining

# 3. По часам и прогноз
11 for each c: caps[c][h] ← alloc[c] · profile[h] / Σ profile   (точно до микрорубля)
12 expected[c][h] ← Алгоритм 1 по часам с caps[c][h]
13 return caps, expected, remaining
```

Сумма `expected` по часам — утверждённая траектория плана. С ней потом сравнивается факт.

## Алгоритм 3. Задача B: цель → бюджет

```text
Вход:  target (число охватов / кликов / конверсий), horizon, channels
Выход: минимальный бюджет и план, либо отказ с максимумом достижимого

1  upper ← суммарная полезная ёмкость каналов в деньгах
2  if metric(Алгоритм 2 с бюджетом upper) < target:
3      return отказ, max_achievable = metric(upper)
4  бинарный поиск по целым рублям в [0, upper]:
5      наименьший budget, при котором metric(Алгоритм 2 с budget) ≥ target
6  return budget, план
```

## Алгоритм 4. Обучение на истории прошлых кампаний

Запускается в момент построения плана, отдельно для каждого канала. История — список прошлых
кампаний на этом же рынке, от старой к новой. По каждой: 24 бина по часу суток (hours, requests,
imps, reach, clicks, conv, spend) и ряд по дням с накопленными R и I на начало дня.

```text
Вход:  channel из каталога, history = [campaign_1 … campaign_J]
Выход: channel с обновлёнными параметрами

1  w_j ← 0.7^(J − j)                                # свежая кампания весит 1, старее — меньше

# Шаг A. Параметры насыщения по дневным рядам
2  для каждого дня d каждой кампании: depth_d, excess_d из R_d, I_d (строки 1–2 Алгоритма 1)
3  ctr_fatigue, freq_fatigue ← регрессия  log(clicks_d/imps_d) = b − ctr_fatigue·depth_d − freq_fatigue·excess_d
4  price_growth              ← регрессия  cpm_d / cpm_0 − 1 = price_growth · depth_d²
5  reach_decay, freq_reach_decay ← регрессия  log(reach_d/imps_d) = reach_decay·log(1−depth_d) − freq_reach_decay·excess_d
   # каждая регрессия взвешена показами дня · w_j и притянута к каталожному значению (ridge):
   # если кампании не выкупали аудиторию глубоко, параметры остаются каталожными

# Шаг B. Снять насыщение с наблюдённых ставок
6  for each campaign j:
7      прогнать Алгоритм 1 по часам кампании с её средним расходом по часу суток
8      ratio_ctr_j ← (модельные clicks / imps) / ctr ;  ratio_cpm_j ← (модельный spend / imps) / cpm
9      clicks_j ← clicks_j / ratio_ctr_j ;  conv_j ← conv_j / ratio_ctr_j ;  spend_j ← spend_j / ratio_cpm_j
   # иначе усталость учлась бы дважды: в данных и снова в прогнозе

# Шаг C. Ставки как взвешенное среднее с каталогом
10 ctr ← (Σ w_j·clicks_j + 1000·ctr_catalog) / (Σ w_j·imps_j + 1000)
11 cr  ← (Σ w_j·conv_j  +   50·cr_catalog)  / (Σ w_j·clicks_j + 50)
   # 1000 показов и 50 кликов — «вес» каталога; одна кампания даёт миллионы показов

# Шаг D. Цена, ёмкость, профиль — смесь с каталогом, доверие растёт с объёмом данных
12 conf_cpm ← min(Σ w_j·imps_j / 100 000, 0.95)
13 cpm ← cpm_catalog · (observed_cpm / cpm_catalog)^conf_cpm
14 rate[h] ← Σ_j w_j·requests_{j,h} / Σ_j w_j·hours_{j,h}        # запросов в час по часу суток
15 conf_sup ← min(Σ w_j·hours_j / 168, 0.95)
16 daily_capacity ← daily_capacity_catalog · (Σ_h rate[h] / daily_capacity_catalog)^conf_sup
17 profile[h] ← нормировать((1 − conf_sup)·profile_catalog[h] + conf_sup·rate[h]/Σ rate)
18 return channel
```

Запросы (строка 14) симулятор отдаёт даже в канале без бюджета, поэтому ёмкость учится честно и по
каналам, куда не вкладывались.

## Алгоритм 5. Каждый час кампании: калибровка и перепланирование

```text
Вход:  approved      — утверждённый план: kpi_target, budget_by_channel
       facts         — накопленные факты по каналам
       recent[−72:]  — последние часы по каналам (requests, imps, reach, clicks, conv, spend)
       history       — как в Алгоритме 4
Выход: caps на оставшиеся часы

# Шаг A. Калибровка каждого канала
1  channel ← Алгоритм 4(каталог, history)                    # prior
2  shock ← «последние 6 часов расходятся с предыдущими 12+»
          по CTR (биномиальный z > 3), по CPM (> 25 %) или по спросу (> 35 %)
3  window ← последние 6 часов if shock else recent            # забыть всё до скачка
4  веса часов в window: 0.5^(возраст_часа / 24)
5  mult ← множители насыщения при текущих R, I (строки 1–3, 6 Алгоритма 1)
6  ctr ← (Σ clicks/mult_ctr + strength·ctr_prior) / (Σ imps + strength)   # strength: 1000 + история, ≤ 31 000
7  cr, cpm, daily_capacity — аналогично строкам 11–16 Алгоритма 4, но по window
8  if requests в последних 6 часах = 0: daily_capacity ← 1 % каталожной   # канал на паузе

# Шаг B. Удержание плана
9  remaining ← budget − spent
10 hold ← остаток budget_by_channel, отмасштабированный на remaining      # утверждённая смесь
11 maxi ← Алгоритм 2 на remaining с калиброванными каналами               # максимум KPI
12 on_plan(x) ≡ прогноз финала (факты + Алгоритм 1 по x) даёт KPI ≥ 0.98·kpi_target
                и расход ≥ 0.99·budget
13 if on_plan(hold):      alloc ← hold                 # на плане: ничего не перекладываем
14 elif not on_plan(maxi): alloc ← maxi                # отстаём даже при максимуме: максимизируем
15 else: λ* ← min λ ∈ [0,1] : on_plan((1−λ)·hold + λ·maxi)   (бинарный поиск)
         alloc ← (1−λ*)·hold + λ*·maxi                 # минимальный сдвиг, возвращающий на план
16 return caps по часам из alloc (строка 11 Алгоритма 2)
```

Пауза канала попадает в условие по расходу (строка 12): утверждённая смесь не может потратить
деньги, и бюджет сдвигается в другие каналы ровно настолько, чтобы их потратить. Деньги никогда не
переводятся в заведомо худший канал и не сжигаются ради «попадания в план». Без `approved` в запросе
работает только строка 11 — чистая максимизация (режим `adaptive_max` в harness).

## Как меряем

```text
frozen:   caps утверждённого плана без изменений          → ошибка прогноза планнера
adaptive: Алгоритм 5 каждый час                            → качество исполнения
метрика:  (fact_T − plan_T) / plan_T в конце кампании, отдельно spend и KPI, порог 20 %
пары:     тот же мир, тот же план, тот же шок → разница объясняется только режимом
```

Считает harness в [`../tools/evaluation/`](../tools/evaluation/README.md).

## Обозначения

| Символ | Смысл |
|---|---|
| `R`, `I` | накопленные уникальный охват и показы канала |
| `depth` | глубина выкупа аудитории, 0 до порога, 1 при полном выкупе |
| `excess` | сколько показов на человека сверх одного |
| `profile[h]` | доля дневного спроса в час суток `h`, сумма 1 |
| `w_j` | вес прошлой кампании по давности |
| `strength` | сколько показов текущей кампании нужно, чтобы перевесить prior |
| `hold`, `maxi` | распределение остатка по утверждённой смеси и по максимуму KPI |

## Чего нет

Охват между каналами не дедуплицируется. Размер аудитории канала не учится, берётся из каталога.
Дрейф рынка между кампаниями история не ловит, только уровень. VTR не моделируется.
